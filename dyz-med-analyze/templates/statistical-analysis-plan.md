# 统计分析计划书（Statistical Analysis Plan）模板

用途：在统计脚本生成与执行之前，把分析计划以人类可读方式呈现给用户确认。只有当用户明确批准计划后，
才进入脚本生成与执行阶段。本模板最后一节记录确认动作及后续变更。

## 1. 基本信息

| 项目 | 内容 |
|------|------|
| 稿件/课题名称 | 待填写 |
| 数据文件路径 | 待填写（绝对路径） |
| 数据字典是否提供 | 是 / 否 |
| 研究设计 | RCT / 队列 / 病例对照 / 横断面 / 诊断准确性 / 系统综述meta分析 / 其他 |
| 计划撰写日期 | YYYY-MM-DD |
| 数据版本/哈希 | 待填写 |
| 计划版本 | v0.1 |
| 计划确认状态 | 待确认 / 已确认（见第8节） |

## 2. 研究问题

- 主要研究问题（PICO 或等价表述）：待填写
- 次要研究问题（如有）：待填写
- 比较框架：优效性(superiority) / 非劣效性(non-inferiority，需预设界值Δ=___) /
  等效性(equivalence，需预设界值=___) / 仅估计(estimation only，无假设检验)

## 3. 变量定义

| 变量名 | 角色 | 类型 | 定义/取值说明 | 缺失编码 | 置信度 |
|--------|------|------|--------------|----------|--------|
| 例：treatment_group | 暴露/干预 | 二分类 | 1=治疗组, 2=对照组 | 999 | 高/中/低 |
| 例：death_1year | 主要结局 | 二分类 | 1年内全因死亡 | | 高 |
| 例：age | 协变量 | 连续 | | | 高 |

置信度为"中"或"低"的变量，需在下方单独列出，等待用户确认角色分配，不直接进入正式计划。

- 变量名：不确定的原因，需要用户说明什么

## 4. 统计方法选择及理由

| 分析目标 | 分析人群 | 效应量与区间 | 拟用方法/软件 | 选择理由 |
|---------|---------|-----------|---------------|---------|
| 主要结局分析 | 例：预设主要分析集 | 例：HR + 95% CI | 例：Cox比例风险回归 / R | 结局为时间-事件数据且存在删失 |
| 基线特征描述 | 全部纳入对象 | 描述性统计 | 例：R | 不做基线显著性筛选 |

关键假设与诊断证据（按实际模型选择，计划阶段只填拟评估内容，不预填通过）：

| 分析目标/模型及评估对象 | 拟用评估方法与适用条件 | 计划输出定位 | 资料不足或发现问题时的处置与审批 |
|---|---|---|---|
| 例：主要结局Cox模型的比例风险 | 结合研究问题评估全局及相关协变量；可用Schoenfeld残差检验与时间趋势图，说明各自适用性与局限 | diagnostics.md对应小节及实际图/输出文件 | 记录问题、评估影响并回到计划；分层Cox或RMST等仅为需论证并获批的候选，不自动替换 |

执行后在本节续填或链接已有 `diagnostics.md` 的同一模型记录，不另造一套诊断结论：

| 模型/评估对象 | 实际方法及观察结果 | 输出/图定位 | 适用假设、局限与不一致 | 证据状态及处置/批准记录 |
|---|---|---|---|---|
| 待执行 | 待填写；如有检验，记录统计量/P值，但不以P值独立判定假设成立 | 实际执行后填写 | 待评估 | 未执行/已评估/发现问题/待核实（unverified）；记录获批处置或待确认事项 |

例如Cox比例风险、Logistic分离/收敛或线性模型残差应按模型和问题选择适用检查，不要求每项分析完成
所有可能诊断。单个P=0.42不能证明比例风险假设成立；检验与图形证据不一致时保留冲突。缺诊断资料标为
`unverified`，不是模型无效的证明；任何变更需按第8节获得确认，不自动换模型。

## 7. 计划外分析与结构化结果交接

任何未在本计划书中预先说明、看到数据后才追加的分析，记录在此，并在讨论部分明确标注为探索性/事后分析，
不包装成预设的主要分析。

| 分析内容 | 出现原因 | 状态 |
|---------|---------|------|
| 例：亚组分析（按年龄分层） | 例：审稿人可能关心的交互作用，非预设 | 探索性/事后 |

### 结构化结果交接（执行后填写，不预填结果）

- 工件身份：`id=analysis-results`；`path`为实际相对项目根目录路径，兼容
  `paper/data/stats/analysis-results.json`、`analysis-results.yaml`及已有`structured_results.yaml`。
  文件名不是身份，不改用户既有路径；登记非空`version`和实际字节`sha256`。
- 每项最小字段：`analysis_id`（稳定且唯一）、`population`、`outcome`、`timepoint`、
  `groups:{comparison,reference}`、`effect_scale`、`unit`、`estimate`、`ci`、`denominator`、
  `source:{artifact_id,locator}`、`execution_status`。人群/时间窗/参考组使用明确口径，不凭列名推断。
- `estimate`为有限十进制数（精确值优先十进制字符串）；`ci`为
  `{lower,upper,level,adjustment,method}`，level用0到1之间比例；`denominator`为
  `{value,kind,unit}`，kind为`count`（非负JSON整数，精确相等）或`continuous`（例如人年）。
- `groups/estimate/ci/denominator`不适用可为null，并在`not_applicable`中按同名键说明理由；
  其中estimate不适用仅供其他数值如事件数的对账，不为其补造估计。尚未提供与不适用必须分开。
- 可选字段：`events`为非负JSON整数；`p:{value,adjustment,method}`独立记录P值及调整/检验口径；
  `model`、`adjustment_set`、结局层级、诊断定位等按方法适用性保留，不要求所有模型统一结构。
  合法调整P值与未调整CI可以并存，不强行套同一算术关系，不自动互换HR/OR/RR。
- `source`引用实际执行输出的已登记工件及位置，接受外部统计人员/软件的输出；不能要求重跑本技能。
  `execution_status=completed`只声明执行完成，其他`not_run/blocked/failed`或未知状态不能写作已核实结果。
- 对账对手为有稿件/表格工件定位的`reported-values`清单；该清单和实际稿件、来源输出均绑定版本/哈希。
  非整数默认精确比较；如确需展示舍入，逐值显式记录小数位数和half_up/half_even规则，无通用宽容差。
- JSON对账工具不自动解析YAML/Word/PDF；如需规范化派生JSON，保留原件，显式映射派生ID并登记原件。
  机器一致只覆盖清单范围；人工摘录完整性、模型适用性和科学解释另核实。检查报告与其独立哈希引用分开。

## 8. 确认记录（执行前必填）

在收到针对当前计划版本的明确人类批准并核实来源前，不会生成并执行针对原始数据的 R 脚本。
单个“已确认”标签或`plan_approved: true`不能替代批准来源。

| 项目 | 内容 |
|------|------|
| 确认人 | 用户姓名/角色 |
| 确认方式及来源 | 人类明确陈述、角色/化名、保存的确认记录路径/哈希及消息或段落定位；不得编造 |
| 批准对象 | 计划稳定artifact_id、version、sha256；批准动作和限制与本次执行一致 |
| 确认日期 | YYYY-MM-DD |
| 确认时提出的修改意见（如有） | |

计划变更时增加版本，记录变更原因、是否看过结果以及重新确认信息；不要覆盖原版本。
